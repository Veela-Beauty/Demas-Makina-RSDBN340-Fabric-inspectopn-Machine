Shared reality for every browser approach: the box must reach the ERPNext server over the network (our tunnel already proves it does), and Chromium 109 uses ~300–500 MB — tight in 1 GB. So in every option the native tunnel tabs stay as the always-available, lightweight machine path; the embedded browser is an added view, not a replacement.
In-window = rendered inside the app frame (not a separate window) Self-contained = no runtime we must install separately on the box
Prototype for comparison only — pick an approach, then we spec + build. Native embedding behaviour (reparenting, WebView2 docking) can't be fully shown in HTML; the mocks illustrate the resulting UX, and the spec sheet carries the real trade-offs.
